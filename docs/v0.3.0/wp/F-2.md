## Decisions

### The cap (gap 1)

- **What counts.** A lost attempt is a helper whose change was discarded (by the lead or the
  owner) or could not be saved (`sealFailure`, counted while it waits too). Merged and no-change
  work never counts, so a well-behaved lead is never limited.
- **Per plan step.** A step is the helper node a `start_agent` resolves to, plus the role the
  lead names (case and spacing aside). It may lose `stepAttemptLimit` = max(2, 1 +
  `maxReworkRounds`) attempts: 3 with the default 2 rounds. That is times the approved plan's
  steps with that node and role (at least one).
- **Per run.** `stepAttemptLimit` × the approved plan's steps (at least one). This stops a lead
  that renames the role on every try.
- **Past either**, `start_agent` is refused with the new refusal code `attempts-exhausted`
  (409). The message tells the lead to decide what waits, hand over with `request_review` and say
  what is missing; the owner decides. `request_review` is accepted then (tested).
- **Why not per node only.** A node (the helper pool) usually takes every step, so the cap would
  grow with the plan. T-1's engine case has a three-step plan and still expects a one-step bound.
- **Fit with T-1's `[bounded]`.** That bound (`plan steps × (1 + rounds) + 1` starts) holds: 3
  starts for one lost step.

### The push target (gap 4)

- **The address, not the name.** Every push for the owner (Push & open PR, a new branch's push,
  the push after creating a repository, the delete on origin) goes to `remote.origin.url`, passed
  as the address. Git never reads `remote.origin.pushurl` then, on any version. `-c
remote.origin.pushurl=…` would not do: push URLs add up, so git would push to both.
- **The address must be one the app recognises**: `parseRemoteUrl` (an `https`, `ssh`, `git` or
  scp-like `owner/name` address), or a local folder, else `push-rejected`. It is not limited to
  GitHub: "Also push" and the delete also serve other origins. `protocol.ext` and `protocol.fd`
  are off for these pushes.
- **`url.<x>.pushInsteadOf`** matching that address is refused with a plain message. It can only
  send pushes somewhere other than where `origin` is fetched from. It cannot be neutralised with
  `-c`: an equally long rule from the repository's config wins over a command-line one.
- **`url.<x>.insteadOf` still applies**, as it does to the owner's own fetches. An ssh rewrite
  of GitHub addresses is common, and the test harness's bare `origin` uses one. A planted one would
  redirect fetches too. Planting it is denied by F-1's guard (`git config` writes) and, in Full
  auto, by the sandbox's git directories.
- **What `--set-upstream origin` did**, the app does after the push: `refs/remotes/origin/<b>`
  set to the pushed commit, and `branch.<b>.remote` / `.merge`. A failure there is only logged.
  The push sends the exact commit read before it (`<commit>:refs/heads/<b>`).

## Proposed ADR amendments (for the coordinator; not applied)

> **ADR-0021, amendment 2026-10-24 (F-2: bounded retries, work that could not be saved).**
>
> 1. A change whose seal failed for any reason keeps why (`sealFailure`): `branch-changed` (F-1),
>    `invalid-workspace` (the folder is gone, or it committed files the app never saves) or
>    `not-saved`. Except for F-1's `branch-changed`, which goes to the lead (`decision`), it
>    waits for the owner (`needs-owner`). The lead may discard any of them and may never merge or
>    rework them. The owner keeps every action.
> 2. A lost attempt is a helper whose change was discarded or could not be saved.
>    - A plan step (the helper node a start resolves to, and the role the lead names) may lose
>      `max(2, 1 + maxReworkRounds)` attempts, times the approved plan's steps with that node and
>      role.
>    - A run may lose that many times its approved plan's steps.
>    - Past either, `start_agent` is refused (`attempts-exhausted`) and the lead hands over.
>    - Merged and no-change work never counts.
> 3. A merge refused because the ticket branch moved outside the app (`ticket-branch-moved`) or is
>    checked out in another folder (`ticket-branch-checked-out`) sends the change to the owner at
>    once. The lead is told not to retry; only the owner can reset (F-1 §4) or free the branch. A
>    merge that fails for another git reason goes to the owner after three failures in a row.
> 4. (Amends F-1's item 1.) The command guard's reader lives in `@acp/core` (`checkGitCommand`).
>    It also reads a shell's input: here-strings and here-documents fed to a shell are read as
>    scripts. A shell reading a pipe or substituted input is denied when the command mentions git.
>    `xargs git` with no subcommand is denied.
>
> **ADR-0017 / ADR-0027, amendment 2026-10-24 (F-2).** The command guard runs before the
> `run-harness-check` rule, so a harness check (or any command) that is branch-managing git is
> never pre-approved for an agent, in any mode. The harness status lists a warning for each check
> or setup step that is branch-managing git. The app's own check runner is unchanged; see the
> follow-ups.
>
> **ADR-0025, amendment 2026-10-24 (F-2: where the owner's pushes go).** Every push the app makes
> for the owner goes to `origin`'s configured address (`remote.origin.url`), passed as the
> address, never the remote name, so a `remote.origin.pushurl` is never used. That covers Push &
> open PR, a new branch's push, the push after creating a repository, and the delete on origin.
> The address must be a recognised repository address or a local folder, and `ext::` and `fd::`
> are off. A `url.<x>.pushInsteadOf` rewrite of it is refused, and `url.<x>.insteadOf` applies as
> for fetches. After a push, the app sets the remote-tracking ref and the branch's upstream
> (`origin`), as `--set-upstream origin` did.

## Known gaps / follow-ups

- **The app's own check runner** still runs a check or setup step that is branch-managing git, if
  the manifest has one. The owner is warned, and agents are never pre-approved to run it. Refusing
  it in `harness/runner.ts` would be a small follow-up.
- **A planted `url.<x>.insteadOf`** in the repository's config would redirect the owner's
  fetches and pushes alike. Planting it is denied by the guard and, in Full auto, by the sandbox.
- **`sealFailure` and `failedMerges` are in memory**, like F-1's. After a restart a change is
  `needs-owner` and only the owner decides. Lost attempts by discard are still counted, since the
  change state is persisted.
- **"Request changes" after the cap.** A step whose attempts are used up stays refused when the
  owner sends the run back. The lead hands over again, and the owner can discard and start a new
  run.
- **Over-blocking, on the safe side**:
  - a pipe into a shell when the command mentions git (`git log | sh -c 'wc -l'`);
  - `xargs git --version`;
  - here-document lines that read as git commands (as before).
- **Programs that run git themselves** (`python -c`, scripts) are still unseen by the guard, as
  F-1 noted.
- **Shared scratchpad.** This agent's helper scripts and commit messages are in `scratchpad/f2/`.
