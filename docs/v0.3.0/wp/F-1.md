# F-1: helpers never manage branches (safety fix)

> Progress file for F-1. Only its agent edits it.
>
> Incident on 2026-10-24, ticket ACPGIT-3, seen through the app's API and read-only git:
>
> - **Setup.** Full auto, with the OS sandbox on.
> - **What the helpers did.** The ticket said "checkout a branch from dev", and the
>   auto-approved plan told the helper to run `git checkout -b … dev` and commit. Two helpers did.
>   Both worktrees ended up on the ticket branch, and the branch moved outside the app.
> - **What followed.** The seal failed (`workspace-branch-changed`) and the changes became
>   `needs-owner`. The lead could neither rework nor discard them, so it started a replacement
>   helper, which did the same: a loop.
> - **The owner's merge and push** refused correctly, because the tip was not the recorded one.
>
> The owner wants helpers and testers never to switch, create, move, commit to, reset or push
> branches. Only the app does that.

## Tasks

- [x] **R. Research.** Why the sandbox let git write the real `.git`, and whether hooks run in
      auto mode. See [f-1-branch-guard-2026-10-24.md](../../research/f-1-branch-guard-2026-10-24.md).
      Claude Code 0.3.296 adds a linked worktree's common git directory to the sandbox's
      `allowWrite` by itself. It denies only `hooks`, `config` and similar files there, so `HEAD`,
      `refs` and `objects` were writable. PreToolUse hook denials short-circuit before the
      permission pipeline, auto mode included.
- [x] **1a. Enforce, in the adapter** (`managed/branch-guard.ts`). For every worker and tester,
      in every approval mode:
  - a PreToolUse hook on Bash that denies branch-managing git and gh commands, with a plain
    message, and never answers `allow`;
  - the gate denies the same commands without asking the owner;
  - `disallowedTools` prefix deny rules (`Bash(git checkout:*)` …).
- [x] **1b. Full auto sandbox.** `FullAutoSpec.gitDirs` is new. The server resolves
      `git rev-parse --git-dir --git-common-dir` in the worktree at spec time
      (`WorkspaceManager.gitDirs`, which fails closed). The adapter adds both folders to
      `filesystem.denyWrite` and to `Edit(//…/**)` rules.
- [x] **2a. Tell helpers and the tester.** `BRANCH_RULE_LINE` goes in the helper brief
      (`helperBrief`) and in the tester brief.
- [x] **2b. Tell the lead and the planner.** `PLAN_BRANCH_LINE` goes in their planning briefs.
- [x] **2c. Plan check** (owner addition, deterministic). `plan-branch-check.ts`
      (`branchCommandIn`, `planBranchCommand`) runs at `submit_plan`, before the owner or Full
      auto approves. The refusal reads: "Plans can't include branch or commit commands: …".
- [x] **3a. Recover from a switched branch.**
  - The seal detects `workspace-branch-changed`. The worktree is detached where it is
    (`detachForeignBranch`), the ticket gets an app line, and the diagnostic
    `helper-branch-changed` is counted.
  - `changeSealed(failure: 'branch-changed')` sends the change to the lead (`decision`, with
    `sealFailure`). Merge, merge anyway and rework are refused. The lead or the owner can discard
    it, and the lead can start a fresh helper.
- [x] **3b. Recover a moved ticket branch.**
  - `TicketBranchDto.movedOutside { tip }` is set on GET `/api/runs/:id/ticket-branch`.
  - POST `/api/runs/:id/ticket-branch/reset` (CSRF, `{ from }`) runs `resetTicketBranch`: guard,
    worktree prune, refused if checked out anywhere, compare-and-swap with `update-ref`.
  - The web shows a warning and "Reset to the last reviewed commit" (`MovedOutsideBanner`).
- [x] **4. Tests and checks** (below). The golden traces are proved to change only by the text.

## Proposed ADR amendment (for the coordinator; not applied)

> **ADR-0021, amendment 2026-10-24 (F-1: the app owns branches).**
>
> 1. Workers and testers never run commands that create, switch, move, commit to, reset, merge,
>    rebase, stash, fetch or push branches, in any approval mode. The adapter enforces this with:
>    - a PreToolUse hook on Bash (it runs before Claude Code's permission pipeline, auto mode
>      included);
>    - the gate's denial without asking the owner;
>    - `disallowedTools` prefix deny rules.
>      The guard is an allowlist. It allows git that reads, git that changes only files and the
>      index of the agent's folder, and listing forms. Everything else is denied, including aliases
>      and `-c`.
> 2. Plans may not contain such steps. `submit_plan` refuses them deterministically, before any
>    approval, owner or automatic. The planning briefs say so, and the helper and tester briefs
>    say the app owns branches and commits.
> 3. A change whose worktree left its own branch (`workspace-branch-changed` at the seal):
>    - is not committed;
>    - its worktree is detached where it is, and no ref moves;
>    - it goes to the lead with that reason (`sealFailure: 'branch-changed'`), or to the owner
>      when no lead is live;
>    - merge and rework are refused, and the lead or the owner may discard it. Discard deletes
>      only the helper's own branch.
> 4. The ticket branch moved outside the app (its tip is not the recorded head):
>    - merge and push keep refusing, as before;
>    - the ticket shows it (`movedOutside`);
>    - the owner may reset it to the recorded head, by `update-ref <recorded> <seen>`
>      (compare-and-swap) after the ticket-branch guard and a worktree prune. This is refused
>      while any worktree has it checked out. No other ref moves.
>
> **ADR-0022, amendment 2026-10-24 (F-1).** Decision 2's `filesystem.denyWrite` also holds the
> worktree's `--git-dir` and `--git-common-dir`. The server resolves them at spec time, absolute
> and as real paths (`FullAutoSpec.gitDirs`). The `Edit` deny rules hold them too. A helper whose
> git folders cannot be resolved does not start (fail closed).
>
> Reason: Claude Code (0.3.296) adds a linked worktree's common git directory to the sandbox's
> writable paths on its own. It denies only `hooks`, `config` and similar files there, so a
> sandboxed `git commit` could write refs and objects (docs/research/f-1-branch-guard-2026-10-24.md).
> The same applies to the tightened sandbox (ADR-0023 §5).

## Known gaps / follow-ups

- **Not yet seen in a real run.** These are verified from the bundled code, not from a real
  run: hook denial in auto mode, and a sandboxed `git commit` failing with the git dirs denied.
  They need the owner's consent for one real run.
- **Programs that run git themselves** (scripts, `python -c`, test runners) are not seen by the
  command guard. They are bounded by the git-dir sandbox deny in Full auto, and by the owner's
  approval in other modes.
- **`sealFailure` is in memory.** After a restart the change is `needs-owner`, like every
  undecided change, and the owner can discard it. There is no persisted reason column, so no
  migration.
- **The reset needs the moved branch free.** It is refused while a helper worktree still has it
  checked out. Old runs from before F-1, like the incident's, need their `needs-owner` changes
  discarded first, which removes those worktrees.
- **Shared scratchpad.** The coordinator's `scratchpad/lint.sh` was overwritten by this agent's
  version (prettier `--check`, then eslint, on the given files). This agent's helper scripts are
  in `scratchpad/f1/`.
