## Behavior and limits

The server prepares target merges and a resolver helper edits conflicted content. Agents do not
receive git authority. Verification and promotion bind evidence to the candidate, target and
policy; changed inputs invalidate that evidence. Existing projects remain manual by default.
Adaptive verification and delegated delivery require explicit project policy.

Recovery uses local target refs, without fetching origin. It starts automatically on supported
reads or local ticket merges, without a timer. Delegated delivery can open or update a GitHub
pull request or merge locally; it does not merge GitHub PRs. Verification statuses distinguish
passed, skipped, unavailable, unverified and stale. See [conflict recovery](../conflict-resolution/STATUS.md)
for implementation and remaining limits.

The knowledge-transfer guide is static documentation. Its token examples do not establish measured
savings, and Codex integration remains planned. The Pages workflow becomes discoverable after
it reaches the default branch; hosting still requires Pages configuration and a manual run.

## Upgrade and rollback

1. Stop the app and its managed runs before upgrading.
2. Back up the database as described in [START.md](../../START.md#stopping-and-upgrading): copy `acp.sqlite`
   and its `-wal` and `-shm` files if present, from your configured data directory to a safe place.
   Keep the files together while the server is stopped.
3. Update to the reviewed release and install with the pinned Node 22 / pnpm 10 toolchain.
   Start with `./start.sh` or the documented development commands.
4. Startup applies migration 0012, adding the `conflict_resolutions` table and indexes.
   Existing projects retain conservative policy defaults.

For rollback, stop the app and restore the pre-upgrade database backup alongside the previous
code version. Do not assume a migrated database is supported by older code or manually remove
migration records.

## Validation and publication

The owner requested tests in PR CI. Local release preparation checks formatting, manifest
consistency, unchanged dependency declarations, and diff integrity; application lint, typecheck,
unit tests, build and browser tests are left to CI. A PR into `main` triggers both `CI / check`
and `CI / e2e`. Their result must be reviewed before merge; no success is claimed in advance.

After review and green CI, a maintainer may merge, tag and publish the release. None of those
publication actions are part of preparing this candidate. Merge the release metadata back into
`dev` before starting the next release so package versions and changelog entries stay aligned.
